This project studies discrete Gaussian sampling as a small, standalone cryptographic component: first a clear scalar implementation, then distribution tests and benchmarks, and only then bitslicing and masking.

Current status: scalar reference scaffold. The sampler is not yet implemented and the code is not suitable for production use.

What discrete Gaussian sampling does

A discrete Gaussian sampler outputs an integer x with probability proportional to exp(−(x − c)² / 2σ²). The center c determines where the distribution is located and σ determines its width. Values near the center are likely; values farther away become exponentially less likely.

Cryptographic code needs more than a curve that looks right. The output probabilities must closely match the target distribution, including its tails, because bias can invalidate the assumptions used in a security proof.

Why a fast implementation matters

Discrete Gaussian sampling is used to generate short, statistically controlled vectors in lattice cryptography. Falcon is a concrete example: its signing procedure samples a short lattice vector from a Gaussian distribution so that signatures do not reveal the secret signing basis. Gaussian samplers also appear in lattice trapdoor algorithms.

Signing may require many coefficient samples, placing the sampler on a frequently executed path rather than in one-time setup. A slow sampler therefore increases signature latency and is especially expensive on small processors. A useful implementation must control the cost of random bits, rejection steps, table access, and arithmetic while preserving the intended distribution.

Why masking is part of the project

Constant-time code limits leakage from secret-dependent branches and memory access, but it does not by itself stop power or electromagnetic measurements from correlating with intermediate values. Masking represents a sensitive value as randomized shares and performs the computation on those shares, making a single physical observation less directly related to the secret.

Masking adds randomness, operations, and verification work. That is why this repository starts with an unmasked scalar reference: establish the distribution and baseline cost first, then compare a 32-sample bitsliced version, and only after that add masking.

Implementation order

  1. Scalar, unmasked Maskaglia reference
  2. Distribution and rejection-rate tests
  3. Baseline benchmark
  4. 32-way uint32_t bitslicing
  5. Masked implementation and side-channel evaluation

HAWK integration and architecture-specific optimization are outside the initial standalone milestone.
